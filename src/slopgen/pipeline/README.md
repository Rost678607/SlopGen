# pipeline

**EN:** The conveyor.

`job.py` — `VideoJob`/`Part`/`Scene`/`BgAsset`/`FgInsert`/`Word`, the state passed between stages. `context.py` — `AppContext`: resolved configs (visuals profile, cast, orchestration, active LLM profile), the LLM client, topic history, and an optional `progress()` sink a stage calls from inside its own loop. `orchestrator.py` — runs a stage chain per video and reports through `on_event` (consumed by both CLI and TUI); one failed video never kills the batch.

Three chains, sharing stage NAMES so checkpoints stay uniform: **info** is idea (skipped when `--idea` was given) → script → tts → footage → subtitles → assemble → metadata; **drama** drops idea, swaps in `drama_script` / `drama_footage` and adds two of its own — `entities` (the visual registry) and `cut` (where the episode boundaries settle, right before anything is generated); **fandom** is the drama chain with `fandom_script` in place of `drama_script` and one stage of its own in front, `canon`, which makes sure the world's compiled reference sheet still matches the lore on disk. `drama.py` plans the shot list: `plan_slots` expands the orchestration into one slot per clip, each pinned to the generator that will make it.

`stages/beats.py` — **what the two narrated modes share.** A beat is one generated clip carrying one piece of narration, and everything about turning a brief into a run of them is the same whoever is speaking: the outline pass that reads the whole brief and cuts it into per-window stretches, the windows themselves, the word budget, the episode boundaries planned as beat numbers, the profanity/visual-notes/ad suffixes. What differs is only WHO narrates and WHAT about — so that is all a mode supplies, as the `Writer` protocol (`empty_brief`, `outline_system`/`outline_user`, `window_system`/`window_user`, `tools`), reading a ready-made `Window` that already knows where in the story it sits and which of its beats close an episode. This was factored out of `drama_script.py` when fandom arrived; that module is now just the drama's half of the contract, and `fandom_script.py` is the fandom's — the same machinery under a narrator who lives inside the world. `fandom_canon.py` is the lazy guard in front of the compile (`llm/lore.py`): under `SMALL_LORE_CHARS` (4000) it compiles nothing and the writer reads the documents whole, and a resumed run keeps the sheet it started on rather than re-planning against lore edited since.

`parts.py` — **the part is the unit of finished work.** A drama split into parts is not made in one sitting: the operator hand-makes episode 1's clips today and episode 2's when tomorrow's free quota resets. So the tail of the chain (footage → subtitles → assemble → metadata, then publish) runs over the episodes whose clips have all arrived, leaves the rest alone, and runs *again* on the next resume — never redoing an episode it has finished. Two rules make that safe: a part is its own timeline (its subtitles start at 0:00 and it is cut into a file of its own, so nothing about episode 2 is needed to finish episode 1), and a part-scoped stage only counts as *done* once every part has been through it, which is what sends a resume back into it. Each episode is published the moment it is cut, and that is recorded on the `Part` so a resume never uploads it twice. An info clip is simply a drama with one part, so both go down the same path. How many parts there are is read off the scene labels, not off `--parts`: the flag is what was asked of the writer, the labels are what the script says — and the operator re-cuts them by dragging the separators at the `script` and `cut` breakpoints. All of this is `parts_iterative`, on by default; turn it off (`--parts-at-once`) and the footage stage refuses to start until every clip is in, which — with no part ever left pending — makes every stage behave as if parts were never separable.

Three ways a run can stop and be picked up again, all on the same checkpoint:
* `checkpoint.py` — every finished stage is written to `<run>/checkpoint.json`, so `--resume` skips what is already on disk and continues from the failure.
* `manual.py` — **operator-supplied footage**, in two flavours that share everything but the instruction. `generate`: slopgen writes a prompt per shot and the operator makes the clip by hand in an external tool. `search`: slopgen writes a brief plus ready-made stock queries (`llm/lookup`, called from each footage stage's `_brief_searches`, which rewrites only the search specs and falls back to the shot description if the call fails) and the operator goes and finds existing material. Either way there is one shotlist, one manifest, one `manual/prompts/*.txt` mirror (`task_text` lays a search task out as brief + `[want, ~Ns]` + queries), one inbox — which takes stills as well as clips, since a search may legitimately come back with a photograph and `attach` records the kind off the delivered file — and one `paused` checkpoint (`slopgen gather`). An info clip waits for every last shot; a drama only waits for the episodes that are short of one.
* `review.py` — breakpoints: after a chosen stage the job parks as `review` and its output is exposed as an editable document (`Doc` of typed `Row`s grouped per scene), folded back by `apply`, which also reports whether the edit made that stage's own output stale (`slopgen review`). A row with `field="part"` is a **part separator**: an item of its own, so the existing move/add/drop machinery re-cuts the drama for free. It is editable at `script` and `cut` and shown read-only wherever else there is something to divide. Fandom adds the `canon` breakpoint: the compiled world as one editable block, the last stop before the script is written against it — and an edit there stays on the job, since it is this run's view of the world while `configs/fandoms/` holds the world itself.

**RU:** Конвейер.

`job.py` — `VideoJob`/`Part`/`Scene`/`BgAsset`/`FgInsert`/`Word`, состояние, идущее между стадиями. `context.py` — `AppContext`: резолвнутые конфиги (профиль видеоряда, каст, оркестрация, активный LLM-профиль), клиент LLM, история тем и необязательный приёмник `progress()`, который стадия дёргает изнутри своего цикла. `orchestrator.py` — гонит цепочку стадий по каждому ролику и докладывает через `on_event` (слушают и CLI, и TUI); падение одного ролика не убивает батч.

Цепочки три, с общими ИМЕНАМИ стадий, чтобы чекпойнты были единообразны: **info** — idea (пропускается при `--idea`) → script → tts → footage → subtitles → assemble → metadata; **drama** выбрасывает idea, подставляет `drama_script` / `drama_footage` и добавляет две свои — `entities` (реестр визуала) и `cut` (где встают границы серий, прямо перед тем, как что-то начнёт генерироваться); **fandom** — та же цепочка драмы, но с `fandom_script` вместо `drama_script` и одной своей стадией впереди, `canon`, которая проверяет, что собранная справка по миру всё ещё соответствует лору на диске. `drama.py` планирует список кадров: `plan_slots` разворачивает оркестрацию в слоты по клипу, каждый закреплён за своим генератором.

`stages/beats.py` — **то общее, что есть у обоих повествовательных режимов.** Бит — это один сгенерированный клип с одним куском озвучки, и всё, что превращает бриф в цепочку битов, одинаково, кто бы ни рассказывал: проход-план, читающий весь бриф и режущий его на отрезки по окнам, сами окна, бюджет слов, границы серий, спланированные номерами битов, дописки про мат, ограничения картинки и рекламу. Разное — только КТО рассказывает и О ЧЁМ, и ровно это режим и поставляет: протокол `Writer` (`empty_brief`, `outline_system`/`outline_user`, `window_system`/`window_user`, `tools`), читающий готовый `Window`, который уже знает, где в истории он находится и какие из его битов закрывают серию. Всё это вынесено из `drama_script.py`, когда появился фандом: теперь тот модуль — только драмовская половина контракта, а `fandom_script.py` — фандомная, та же механика под рассказчиком, живущим внутри мира. `fandom_canon.py` — ленивый сторож перед компиляцией (`llm/lore.py`): меньше `SMALL_LORE_CHARS` (4000) — не компилируется ничего, сценарист читает документы целиком; а продолженный прогон остаётся на той справке, с которой начал, вместо перепланирования по лору, изменённому с тех пор.

`parts.py` — **часть и есть единица готовой работы.** Дорама, разрезанная на части, не делается за один присест: клипы первой серии оператор гонит руками сегодня, второй — когда завтра обновится бесплатная квота. Поэтому хвост цепочки (footage → subtitles → assemble → metadata, дальше публикация) проходит по тем сериям, чьи клипы уже собраны, остальные не трогает и запускается *снова* на следующем `--resume` — никогда не переделывая то, что уже доделал. Безопасным это делают два правила: часть — сама себе таймлайн (её субтитры начинаются с 0:00, и режется она в отдельный файл, так что вторая серия не нужна, чтобы доделать первую), а частеориентированная стадия считается *завершённой*, только когда через неё прошли все части, — именно это заводит резюм обратно в неё. Каждая серия публикуется сразу, как смонтирована, и это записывается на самом `Part`, чтобы резюм не залил её второй раз. Инфо-клип — это дорама из одной части, так что путь у них общий. Сколько частей — читается по меткам сцен, а не по `--parts`: флаг это то, что попросили у сценариста, а метки — то, что он написал; двигает их оператор, таская разделители на брейкпоинтах `script` и `cut`. Всё это — `parts_iterative`, включённый по умолчанию; выключи (`--parts-at-once`), и стадия footage не стартует, пока не собраны все клипы, — а раз ни одна часть не остаётся в ожидании, весь конвейер ведёт себя так, будто части и не делились.

Прогон может встать и быть продолжен тремя способами, все на одном чекпойнте:
* `checkpoint.py` — каждая законченная стадия пишется в `<прогон>/checkpoint.json`, поэтому `--resume` пропускает готовое и продолжает с места падения.
* `manual.py` — **материал от оператора**, в двух видах, у которых различается только инструкция. `generate`: слопген пишет промпт на кадр, оператор делает клип руками во внешнем сервисе. `search`: слопген пишет бриф и готовые запросы для стоков (`llm/lookup`, вызывается из `_brief_searches` каждой стадии видеоряда — та переписывает только поисковые спеки, а при сорвавшемся запросе оставляет описание кадра), а оператор идёт искать уже существующий материал. И там и там один шотлист, один манифест, одно зеркало `manual/prompts/*.txt` (`task_text` раскладывает поисковую задачу как бриф + `[want, ~Nс]` + запросы), один инбокс — принимающий не только клипы, но и неподвижные кадры, потому что поиск законно может вернуться с фотографией, и `attach` записывает вид по принесённому файлу, — и один чекпойнт `paused` (`slopgen gather`). Инфо-клип ждёт все кадры до последнего; дорама ждёт только те серии, которым чего-то не хватает.
* `review.py` — брейкпоинты: после выбранной стадии задача встаёт в `review`, а её результат выдаётся редактируемым документом (`Doc` из типизированных `Row`, сгруппированных по сценам), который `apply` складывает обратно и заодно сообщает, устарел ли от правки результат самой стадии (`slopgen review`). Строка с `field="part"` — это **разделитель частей**: отдельная позиция, поэтому уже существующая механика «двигать/добавить/удалить» бесплатно перекраивает дораму. Он редактируемый на `script` и `cut` и показан только для чтения везде, где ещё есть что делить. Фандом добавляет брейкпоинт `canon`: собранный мир одним редактируемым блоком, последняя остановка перед тем, как по нему напишут сценарий, — и правка остаётся на задаче, потому что это взгляд на мир одного прогона, а сам мир лежит в `configs/fandoms/`.
