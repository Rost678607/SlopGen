# pipeline

**EN:** The conveyor.

`job.py` — `VideoJob`/`Part`/`Scene`/`BgAsset`/`FgInsert`/`Word`, the state passed between stages. `context.py` — `AppContext`: resolved configs (visuals profile, cast, orchestration, active LLM profile), the LLM client, topic history, and an optional `progress()` sink a stage calls from inside its own loop. `orchestrator.py` — runs a stage chain per video and reports through `on_event` (consumed by both CLI and TUI); one failed video never kills the batch.

Two chains, sharing stage NAMES so checkpoints stay uniform: **info** is idea (skipped when `--idea` was given) → script → tts → footage → subtitles → assemble → metadata; **drama** drops idea, swaps in `drama_script` / `drama_footage` and adds two of its own — `entities` (the visual registry) and `cut` (where the episode boundaries settle, right before anything is generated). `drama.py` plans the shot list: `plan_slots` expands the orchestration into one slot per clip, each pinned to the generator that will make it.

`parts.py` — **the part is the unit of finished work.** A drama split into parts is not made in one sitting: the operator hand-makes episode 1's clips today and episode 2's when tomorrow's free quota resets. So the tail of the chain (footage → subtitles → assemble → metadata, then publish) runs over the episodes whose clips have all arrived, leaves the rest alone, and runs *again* on the next resume — never redoing an episode it has finished. Two rules make that safe: a part is its own timeline (its subtitles start at 0:00 and it is cut into a file of its own, so nothing about episode 2 is needed to finish episode 1), and a part-scoped stage only counts as *done* once every part has been through it, which is what sends a resume back into it. Each episode is published the moment it is cut, and that is recorded on the `Part` so a resume never uploads it twice. An info clip is simply a drama with one part, so both go down the same path. How many parts there are is read off the scene labels, not off `--parts`: the flag is what was asked of the writer, the labels are what the script says — and the operator re-cuts them by dragging the separators at the `script` and `cut` breakpoints.

Three ways a run can stop and be picked up again, all on the same checkpoint:
* `checkpoint.py` — every finished stage is written to `<run>/checkpoint.json`, so `--resume` skips what is already on disk and continues from the failure.
* `manual.py` — the user-assisted (`manual`) generator: slopgen writes a shotlist and prompts, the operator makes the clips by hand in an external tool, and the job parks as `paused` (`slopgen gather`). An info clip waits for every last shot; a drama only waits for the episodes that are short of one.
* `review.py` — breakpoints: after a chosen stage the job parks as `review` and its output is exposed as an editable document (`Doc` of typed `Row`s grouped per scene), folded back by `apply`, which also reports whether the edit made that stage's own output stale (`slopgen review`). A row with `field="part"` is a **part separator**: an item of its own, so the existing move/add/drop machinery re-cuts the drama for free. It is editable at `script` and `cut` and shown read-only wherever else there is something to divide.

**RU:** Конвейер.

`job.py` — `VideoJob`/`Part`/`Scene`/`BgAsset`/`FgInsert`/`Word`, состояние, идущее между стадиями. `context.py` — `AppContext`: резолвнутые конфиги (профиль видеоряда, каст, оркестрация, активный LLM-профиль), клиент LLM, история тем и необязательный приёмник `progress()`, который стадия дёргает изнутри своего цикла. `orchestrator.py` — гонит цепочку стадий по каждому ролику и докладывает через `on_event` (слушают и CLI, и TUI); падение одного ролика не убивает батч.

Цепочки две, с общими ИМЕНАМИ стадий, чтобы чекпойнты были единообразны: **info** — idea (пропускается при `--idea`) → script → tts → footage → subtitles → assemble → metadata; **drama** выбрасывает idea, подставляет `drama_script` / `drama_footage` и добавляет две свои — `entities` (реестр визуала) и `cut` (где встают границы серий, прямо перед тем, как что-то начнёт генерироваться). `drama.py` планирует список кадров: `plan_slots` разворачивает оркестрацию в слоты по клипу, каждый закреплён за своим генератором.

`parts.py` — **часть и есть единица готовой работы.** Дорама, разрезанная на части, не делается за один присест: клипы первой серии оператор гонит руками сегодня, второй — когда завтра обновится бесплатная квота. Поэтому хвост цепочки (footage → subtitles → assemble → metadata, дальше публикация) проходит по тем сериям, чьи клипы уже собраны, остальные не трогает и запускается *снова* на следующем `--resume` — никогда не переделывая то, что уже доделал. Безопасным это делают два правила: часть — сама себе таймлайн (её субтитры начинаются с 0:00, и режется она в отдельный файл, так что вторая серия не нужна, чтобы доделать первую), а частеориентированная стадия считается *завершённой*, только когда через неё прошли все части, — именно это заводит резюм обратно в неё. Каждая серия публикуется сразу, как смонтирована, и это записывается на самом `Part`, чтобы резюм не залил её второй раз. Инфо-клип — это дорама из одной части, так что путь у них общий. Сколько частей — читается по меткам сцен, а не по `--parts`: флаг это то, что попросили у сценариста, а метки — то, что он написал; двигает их оператор, таская разделители на брейкпоинтах `script` и `cut`.

Прогон может встать и быть продолжен тремя способами, все на одном чекпойнте:
* `checkpoint.py` — каждая законченная стадия пишется в `<прогон>/checkpoint.json`, поэтому `--resume` пропускает готовое и продолжает с места падения.
* `manual.py` — user-assisted генератор (`manual`): slopgen пишет шотлист и промпты, оператор делает клипы руками во внешнем сервисе, а задача стоит в `paused` (`slopgen gather`). Инфо-клип ждёт все кадры до последнего; дорама ждёт только те серии, которым чего-то не хватает.
* `review.py` — брейкпоинты: после выбранной стадии задача встаёт в `review`, а её результат выдаётся редактируемым документом (`Doc` из типизированных `Row`, сгруппированных по сценам), который `apply` складывает обратно и заодно сообщает, устарел ли от правки результат самой стадии (`slopgen review`). Строка с `field="part"` — это **разделитель частей**: отдельная позиция, поэтому уже существующая механика «двигать/добавить/удалить» бесплатно перекраивает дораму. Он редактируемый на `script` и `cut` и показан только для чтения везде, где ещё есть что делить.
