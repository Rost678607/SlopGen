# tui

**Rows of buttons (`ButtonRow`):** every action bar and tab strip is a `ButtonRow`, never a bare `Horizontal`. Textual's horizontal layout gives each child its natural width and silently clips whatever runs past the container — which is invisible while developing in English and breaks in Russian, where the same labels run 20-30% longer. Measured across this app before the fix: 63 clipped buttons at ordinary terminal widths, and the character editor's "+ new" tab was cut off by 65 columns, meaning a cast of six could not be added to at all. A `ButtonRow` is a grid whose column count is recomputed on every resize — as many equal columns as fit the WIDEST button, which is what makes "no label is ever truncated" a guarantee rather than a hope — and the overflow wraps onto further rows. Call `repack()` after mounting buttons into an existing row: a tab bar gains a tab without the container resizing, so `on_resize` never fires. Action bars stretch their buttons to the cell; `.tabbar` keeps them at their own width, because a two-letter tab blown up to the longest name stops looking like a tab.

**Form kit (`forms.py`):** screen controls are *declared*, not hand-wired. A `Form` holds a list of `Field`s (`Text` / `Number` / `Range` / `Choice` / `Toggle` / `Heading` / `Note`, plus `Group` for a gated sub-section) and can build its widgets (`compose`/`build`), read every value back typed (`read` → dict), prefill from a dict (`fill`), and toggle each `Group` from a predicate over the current values (`refresh_visibility`, which also scrolls a freshly-revealed group into view). `FieldTextArea` is the single text-field object: regular fields self-size from one to five rows and treat Enter as "next field", `large=True` fields are pinned to five rows and scroll; `Number` adds `▲`/`▼` steppers for ±1, `Range` renders the slider from `slider.py`, and password fields keep `Input` internally. Widget ids are `{form.ns}-{field.key}`, which is also how the breakpoint screen gives a generated field a positional id. Wizard panes and every config-entity form are built from field lists this way — editing the UI means editing a list.

**EN:** Textual TUI with a custom Minecraft theme and no footer — a custom `TopBar` (title, RU/EN toggle, `<-` back, Palette) docks on every screen; all labels go through the `I18N` table; the theme persists to `[ui].theme`. Screens:

* `HomeScreen` — centered arrow-key menu (Generate / Continue a run / Configuration / Models / Quit).
* `ModeSelectScreen` → `GenerateScreen` (info, 5 steps) or `DramaScreen` (drama, 6 steps: the Story step holds plot + cast, and the Visuals step becomes the orchestration editor). Whatever else that step holds, it ends the same way in all three wizards: the art style, shown only when something in the run is actually generated, and under it the montage filters (`_fx_fields`), which are shown always — they are laid over the finished cut and so ask nothing of the source. The Summary step previews the equivalent CLI command and carries the breakpoint switches.
* `ProgressScreen` — the pipeline in a worker thread, over a per-video queue table and live log, with a bar tracking progress *inside* the current stage (voiced fragments, generated clips, assembled scenes) fed by `AppContext.progress`.
* `BreakpointScreen` — master-detail review of a parked stage: items are cards on the left (add / reorder / drop), the open card's typed fields on the right (text, number, choice, and `chips` picked through `PickModal`), an AI edit line under them, and — at the voiceover breakpoint — re-voicing one line in place with playback.
* `ManualGatherScreen` — the shotlist for user-assisted clips: prompts to copy, inbox rescan, attach by path, then resume. Each shot says which kind suits it — the run's medium for a generated shot, the moment's own for a searched one — while making plain that the other kind is taken too and adapted, since the inbox judges a delivery by what ffprobe finds in it rather than by its extension. Files sitting in the inbox that will never be picked up are listed under the tally with the reason (no shot by that name, no picture in the file), because a rescan that takes nothing used to look exactly like a rescan with nothing to take.
* `RunsScreen` — every run under the output folder that left a `checkpoint.json`, newest first (by the checkpoint's own `updated_at` — a folder's mtime moves when a clip is dropped into an inbox by hand, so it is only the fallback), capped at 30. A row is the run's name, its mode/language/world, a tally of its videos (`2× ✘1 ✔1`) and the state that speaks for the whole run with the stage it stopped on; the pane beside it holds the selected run in full and scrolls, because an error there is a traceback and the table cell is one line wide. Continue takes the run through the door it is actually waiting behind — the same three the run screen picks between when a batch parks itself: `review` → `BreakpointScreen`, `paused` → `ManualGatherScreen`, anything else → `ProgressScreen(resume_dir=…)`. It always resumes on the CHECKPOINT's own params, never the wizard's: those are what the run was launched with, down to the breakpoints it has not reached yet, and the checkpoint carries a `reviewed` list so a breakpoint already inspected does not fire a second time. A run whose every video is `done` is still listed, marked finished and refused. This is what used to exist on the CLI alone (`--resume`): a parked run opened its own screen, but only while the interface was still up — close it and a half-finished drama was reachable from the command line only.
* `ModelManagerScreen` — download and remove neural weights: the catalogue on the left, one model's licence, size and reason-for-existing on the right, a progress bar under them. Its own screen rather than a config section because nothing here is a setting — these are gigabytes arriving over a slow link, so the install runs in a worker thread reporting through `call_from_thread` (the same pattern as the run screen's progress) and an interrupted download resumes from the byte it stopped at.
* `ConfigScreen` — sections on the left; `EntityPane` gives each entity kind a tab row per config file plus "+ new", prefilled forms, save and confirmed delete; `TTSPane` and `VoicePane` are the voice half — the first a provider-style cascade (engine → its own settings → key status → whether the recognizer it needs is installed), the second the library of cloned voices with the sample check one button away — including the strict half of it, whether the recording actually says the transcript typed above it, which is the check that catches a sample the model will recite instead of read; `LLMPane` adds provider/model presets, a web-search toggle and a password API-key input persisted to `.env`, plus ★ activation; `CharacterPane` edits the cast library; `FandomPane` edits a world whole — its settings, its lore (with the canon sheet recompiled on save) and its own cast, which `FandomCharacterPane` keeps on a different shelf *and* on a different form: a world's character is a look plus how many of it (one / many identical / a whole kind), never an age and never a personality, so the fields come from `_entity_form("world_characters")` rather than the drama's (see `config/README`). `FootagePane` saves the stock/generator keys.

**RU:** TUI на Textual с темой Minecraft и без футера — на каждом экране свой `TopBar` (заголовок, RU/EN, `<-`, Palette); все надписи через таблицу `I18N`; тема сохраняется в `[ui].theme`. Экраны:

* `HomeScreen` — центрированное меню (Генерация / Продолжить прогон / Конфигурация / Модели / Выход) — со стрелочками.
* `ModeSelectScreen` → `GenerateScreen` (инфа, 5 шагов) или `DramaScreen` (дорама, 6 шагов: шаг «Сюжет» держит замысел и каст, а шаг «Видеоряд» превращается в редактор оркестрации). Чем бы этот шаг ни был занят, заканчивается он во всех трёх мастерах одинаково: стиль графики — только если в прогоне действительно что-то генерируется — и под ним монтажные фильтры (`_fx_fields`), которые видны всегда: они ложатся на готовый монтаж и ничего не спрашивают у источника. Шаг «Итог» показывает эквивалентную CLI-команду и несёт тумблеры брейкпоинтов.
* `ProgressScreen` — конвейер в worker-потоке, над ним таблица очереди по роликам и живой лог, плюс полоса прогресса *внутри* текущей стадии (фрагменты озвучки, сгенерированные клипы, смонтированные сцены), которую питает `AppContext.progress`.
* `BreakpointScreen` — разбор застывшей стадии в виде мастер-детейл: слева карточки позиций (добавить / переставить / удалить), справа типизированные поля открытой карточки (текст, число, выбор и `chips` через `PickModal`), под ними ИИ-строка, а на брейкпоинте озвучки — переозвучка строки на месте с прослушиванием.
* `ManualGatherScreen` — шотлист для ручных клипов: промпты для копирования, пересканирование inbox, привязка по пути, продолжение прогона. У каждого кадра сказано, что ему подходит — медиум прогона для сгенерированного, потребность момента для найденного, — и тут же сказано, что другой вид тоже возьмут и подгонят: инбокс судит принесённое по тому, что в нём находит ffprobe, а не по расширению. Файлы, которые лежат в инбоксе и взяты не будут, перечислены под счётчиком вместе с причиной (нет кадра с таким именем, нет картинки в файле), потому что пересканирование, ничего не взявшее, раньше выглядело ровно как пересканирование, которому нечего брать.
* `RunsScreen` — все прогоны в папке вывода, оставившие `checkpoint.json`, свежие сверху (по собственному `updated_at` чекпоинта: mtime папки двигается и от клипа, положенного в inbox руками, поэтому он лишь запасной вариант), не больше 30. Строка — имя прогона, его режим/язык/мир, счёт роликов (`2× ✘1 ✔1`) и состояние, говорящее за весь прогон, вместе со стадией, на которой он встал; панель рядом держит выбранный прогон целиком и прокручивается, потому что ошибка здесь — это трейсбек, а ячейка таблицы шириной в одну строку. «Продолжить» ведёт в ту дверь, за которой прогон на самом деле ждёт, — те же три, между которыми выбирает экран прогона, когда батч сам встаёт: `review` → `BreakpointScreen`, `paused` → `ManualGatherScreen`, всё остальное → `ProgressScreen(resume_dir=…)`. Продолжение всегда идёт по параметрам ЧЕКПОИНТА, а не мастера: именно с ними прогон был запущен, вплоть до брейкпоинтов, до которых он ещё не дошёл, — а список `reviewed` в чекпоинте не даёт уже разобранному брейкпоинту сработать второй раз. Прогон, где все ролики `done`, всё равно в списке — помечен как завершённый и продолжению не подлежит. Раньше это было только в CLI (`--resume`): вставший прогон открывал свой экран сам, но лишь пока интерфейс не закрыт, — а после закрытия недоделанная дорама доставалась только из командной строки.
* `ModelManagerScreen` — качает и удаляет веса нейронок: каталог слева, лицензия, размер и назначение выбранной модели справа, полоса прогресса под ними. Отдельный экран, а не раздел конфигурации, потому что здесь нет ни одной настройки — это гигабайты, приезжающие по небыстрому каналу, поэтому установка идёт в рабочем потоке и отчитывается через `call_from_thread` (тем же способом, что и прогресс на экране прогона), а оборванная загрузка продолжается с того байта, на котором остановилась.
* `ConfigScreen` — секции слева; `EntityPane` даёт каждому виду сущностей ряд таб-кнопок по файлам плюс «+ новый», предзаполненные формы, сохранение и удаление с подтверждением; `TTSPane` и `VoicePane` — голосовая половина: первый устроен как каскад провайдера (движок → его собственные настройки → статус ключа → установлен ли нужный ему распознаватель), второй — библиотека клонированных голосов, где проверка образца в одну кнопку, включая самую строгую её часть: говорит ли запись то, что набрано в расшифровке над ней, — именно она ловит образец, который модель будет пересказывать вместо чтения; `LLMPane` добавляет пресеты провайдеров/моделей, тумблер веб-поиска и password-ввод ключа с сохранением в `.env`, плюс активацию ★; `CharacterPane` правит библиотеку каста; `FandomPane` правит мир целиком — его настройки, лор (с пересборкой канон-справки при сохранении) и собственный каст, который `FandomCharacterPane` держит на другой полке *и* на другой форме: персонаж мира — это внешность плюс сколько его (один / много одинаковых / целый вид), без возраста и без характера, поэтому поля берутся из `_entity_form("world_characters")`, а не из драмовской (см. `config/README`). `FootagePane` хранит ключи стока и генераторов.

**Ряды кнопок (`ButtonRow`):** все панели действий и полосы вкладок — это `ButtonRow`, а не голый `Horizontal`. Горизонтальная раскладка Textual даёт каждому потомку его натуральную ширину и молча обрезает то, что вышло за контейнер: при разработке по-английски это не видно, а по-русски ломается — те же подписи длиннее на 20-30%. Замерено до исправления: 63 обрезанные кнопки на обычных ширинах терминала, а вкладка «+ новый» в редакторе персонажей срезалась на 65 колонок, то есть каст из шести человек нельзя было пополнить вовсе. `ButtonRow` — это сетка, число колонок в которой пересчитывается на каждом ресайзе: столько равных колонок, сколько влезает по САМОЙ ШИРОКОЙ кнопке, — именно это превращает «ни одна подпись не обрежется» из надежды в гарантию, — а лишнее переносится на следующие ряды. После домонтирования кнопок в существующий ряд зови `repack()`: полоса вкладок получает вкладку без изменения размера контейнера, так что `on_resize` не сработает. В панелях действий кнопки растягиваются на ячейку, в `.tabbar` сохраняют свою ширину: вкладка из двух букв, раздутая до длины самого длинного имени, перестаёт читаться как вкладка.
